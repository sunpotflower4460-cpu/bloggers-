# traps.md — 罠（GPT が既定値に流れやすい場面）

### C-050 見た目の方向性が決まっていないとき

**よくする**
- `docs/00-soul/DESIGN_BRIEF.md` の型と題材の世界から配色・書体を導出する
- 型（tool / ritual / toy）をまず決めてから細部に進む

**よくない**
- 生成AIが既定で着地しやすい以下の3パターンを、ブリーフの指定なしに採用する:
  1. クリーム地（#F4F1EA 近辺）+ 高コントラストのセリフ見出し + テラコッタ系アクセント
  2. ほぼ黒の地 + 単色のアシッドグリーンまたは朱のアクセント
  3. ヘアラインの罫 + 角丸ゼロ + 新聞的な多段組
- 中央寄せヒーロー + グラデーション背景のような、既定値の寄せ集めで済ませる

**なぜ**
上記3パターンは「選択」ではなく学習データの「既定」である。ブリーフが明示的に指定しない限り採用しない。方向性が無いときほど既定値に流れやすいので、この項目を先に引くこと自体が対策になる。

**型による差**
- 道具型: 密度と速さから配色・書体を逆算する
- 儀式型: 余白と静けさから配色・書体を逆算する
- 遊具型: 反応と触感から配色・書体を逆算する

**実例**
docs/00-soul/DESIGN_BRIEF.md

### C-051 情報を強調したいとき

**よくする**
- 余白を広げる、または階層を1段上げることで強調する
- 強調は画面内で最大1〜2箇所に絞る

**よくない**
- 色を増やして目立たせる
- 太字・大文字・下線など複数の強調手段を同時に重ねる

**なぜ**
強調手段を重ねるほど、本当に重要な箇所が埋もれる。強調は希少であるほど機能する。

**型による差**
- 道具型: 位置（固定・先頭）で強調する
- 儀式型: 余白だけで強調し、装飾を足さない
- 遊具型: 動きの一瞬で強調する

**実例**
refs/screens/emphasis/

### C-052 余白が足りないと感じたとき

**よくする**
- 要素そのものを削れないか先に検討する
- `--sp-1`〜`--sp-6` の範囲内で余白を増やす

**よくない**
- スケール外の余白を個別の数値で足す
- 要素を縮小して詰め込み、余白を作らない

**なぜ**
余白不足の多くは余白の問題ではなく要素過多の問題である。トークンの範囲内で足りない場合は、先に削る余地を疑う。

**型による差**
- 道具型: 密度を保ったまま、不要な要素を削って余白を作る
- 儀式型: 余白の広さそのものを積極的に使う
- 遊具型: 余白と触れる要素のコントラストで作る

**実例**
docs/04-design/tokens.css

### C-053 既存デモをリファクタするとき

**よくする**
- `docs/01-intake/DESIGN_INVENTORY.md` でトークンを抽出してから触る
- デモに存在しない画面（空状態・エラーなど）にのみ `craft/` を適用する

**よくない**
- デモの見た目を「洗練させる」目的で書き換える
- 抽出前にトークンを `tokens.css` へ独自の値で書き込む

**なぜ**
持ち込まれたデモの表現は、既定値に見えても意図的な選択である可能性が高い。中央寄せヒーローもグラデーションも、デモにあるなら**壊さない**。判断せず `INVENTORY.md` で確認する。

**型による差**
- 道具型: デモの密度をそのまま尊重する
- 儀式型: デモの間の取り方をそのまま尊重する
- 遊具型: デモの反応の作り方をそのまま尊重する

**実例**
docs/01-intake/DESIGN_INVENTORY.md

### C-054 機能を足したくなったとき

**よくする**
- 思いついた機能は `BACKLOG.md` に書いてその場では実装しない
- 「補強」に該当するか（既存動線の信頼性・エッジケース・手触り）を先に確認する

**よくない**
- 承認済みIDのない機能をその場の判断で実装する
- 「こんなこともできます」の一言とともに機能を追加する

**なぜ**
思いつきの実装は入口を増やし、承認の外側で製品の形を変える。増える入口の数はAGENTS.mdのルール6で機械的に検出される。

**型による差**
- 道具型: 機能追加より既存機能の速度改善を優先して検討する
- 儀式型: 機能を増やさず、既存の1機能を深めることを優先する
- 遊具型: 新しい反応のバリエーションではなく、既存の反応の質を先に見直す

**実例**
docs/03-scope/BACKLOG.md

### C-055 参照実装をそのまま使いたくなったとき

**よくする**
- `refs/` は構造（レイアウト・状態遷移）としてのみ参照する
- 色・書体・余白は必ず `tokens.css` 経由で自分のプロジェクトの値に置き換える

**よくない**
- `refs/` のコードをコピーしてそのまま使う
- `refs/` にある構造をそのプロジェクトのSOULを確認せずに採用する

**なぜ**
`refs/` は見た目を持たない構造見本として作られている。そのままコピーすると見た目が固定化され、v2が解こうとしている「毎回同じ顔になる」問題が再発する。

**型による差**
- 道具型: 密度に関わる構造（行高・グリッド）だけを参照する
- 儀式型: 間に関わる構造（遷移・余白配分）だけを参照する
- 遊具型: 反応に関わる構造（状態遷移・フィードバック位置）だけを参照する

**実例**
refs/structure/README.md
